- 판단: 오픈크랩 결합은 좋다. 단, 오픈크랩은 자동 확정 엔진이 아니라 SKU 속성 근거, 예외 규칙, Human QA 결과, 오답 패턴, 버전별 개선 이력을 구조화해 주는 온톨로지/증거 레이어로 붙인다.
- 권장 구조: `SKU 작업 하네스 에이전트 -> OpenCrab evidence/ontology memory -> BPE 상태 저장 -> Human QA -> Learning Ledger -> 다음 배치 recall`.
- 주의: 롯데 실데이터 외부 전송 금지, AI 자동 확정 금지, 고객 승인 없는 신규 데이터 파이프라인 실행 금지.

## 롯데 프로젝트 - v1/v2 Parity Test 이미지 적용 판단

- 오딘이 `v1-vs-v2 Parity Test: Rollout Mode Support` 이미지와 함께 롯데프로젝트에서도 수행해야 하는지 질문했다.
- 판단: 해야 한다. 단, 코드의 feature flag parity test를 그대로 가져오는 것이 아니라 롯데 하네스의 `정제 결과 동등성/회귀 검증`으로 변환한다.
- 롯데 적용 매핑: `v1 = 기존 수작업/현재 하네스`, `v2 = 보강된 SKU 속성 자동 채움 하네스`, `rollout mode = 일부 카테고리/SKU/속성만 단계적 적용`, `builder gaps = 속성 스키마/근거/룰/검수 UI 누락`.
- 필수 비교 항목: 기존 결과와 신규 결과의 속성값 일치율, confidence 변화, Human QA 발생률, 88코드 영향, 고위험 속성 오답률, 납품 포맷 동일성.
- 권장 실행 순서: synthetic/public SKU 샘플 -> 내부 비식별 샘플 -> 제한된 실제 작업 사본 -> Human QA 후 확대. 자동 확정은 금지하고 Final Human QC Gate를 유지한다.

## 롯데 프로젝트 - 주방/레시피 비유 기반 하네스 설계 원칙

- 오딘이 롯데프로젝트 성공을 위해 하네스 에이전트를 정확히 설계해야 하며, 같은 포맷을 반복해 사용해도 같은 결과가 나오도록 해야 한다고 정리했다.
- 비유: 롯데에 넘겨야 하는 것은 음식 한 접시가 아니라 `주방`, `주방장`, `주방보조원`, `레시피` 전체다. 시스템으로 반복해서 같은 맛, 푸드스타일, 데코레이션이 나오도록 해야 한다.
- 롯데 매핑: `주방 = 실행 환경/데이터 폴더/툴체인`, `주방장 = Orchestrator/판단 책임 에이전트`, `주방보조원 = 속성별 Worker/Verifier`, `레시피 = Runbook/Prompt/Rule/Schema/Test`, `시식/검수 = Human QA/Final QC`, `납품 메뉴판 = Deliverable Format`.
- 설계 원칙: 같은 입력, 같은 버전의 룰/프롬프트/모델/스키마/근거 저장소를 쓰면 같은 결과가 재현되어야 한다. 변경이 있으면 버전과 사유를 Learning Ledger에 남기고 v1/v2 parity test로 품질을 비교한다.
